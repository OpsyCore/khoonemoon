# گزارش بررسی chunkهای Android WebView

این گزارش כולל دو snapshot دارد: وضعیت جاری صفحه‌محور و یک مقایسهٔ تاریخی از build قدیمی‌تر. build جاری با URL عمومی و publishable key همان پروژه ساخته شد؛ هیچ service-role key یا دادهٔ کاربر در build استفاده نشد. حجم‌ها بایت‌اند؛ هر فایل JS جداگانه gzip شده است. CSS، تصاویر، APK و حافظه/سرعت runtime روی دستگاه در اعداد JS نیستند. نام hashها با هر build ممکن است عوض شوند.

هر دو check مستقل اجرا شدند و قبول‌اند. سقف Total برابر 330,000 مطابق تصمیم قبلی است؛ این سقف کنترل رشد bundle است، نه محدودیت Android/WebView. حاشیهٔ Total کم است، بنابراین هر تغییر بعدی باید در CI دوباره budget را بگذراند.

## تصمیم‌های code-splitting جاری

- همهٔ مسیرهای صفحه همچنان dynamic import/on-demand هستند؛ static closure فقط entry و `jsx-runtime` است. برای کاهش مجموع gzip، فرم تسک و رویداد و hook پیگیری مشترک‌شان در `task-event-forms` ادغام شده‌اند. بازکردن هر یک اکنون کد هر دو فرم را هم دریافت می‌کند (حدود 2 KB بیشتر نسبت به بارگذاری مجزای همان فرم)، اما هیچ‌یک وارد Initial نشده‌اند و Total از سقف عبور نمی‌کند.
- آیکون‌های مورد استفادهٔ صفحه‌های deferred در `deferred-icons` گروه‌بندی شده‌اند تا request/chunkهای ریز حذف شوند؛ ورود آیکون تازه به مسیر Initial همچنان با سقف Initial کنترل می‌شود.
- برچسب‌های مناسبت از یک chunk ریزِ runtime به ماژول `occasions` منتقل شده‌اند تا `types` chunk جداگانه تولید نشود.
- مرور sourcemapهای تاریخی فقط نبود چند نسخهٔ تکراری برای React، React DOM، Supabase، Temporal، Zod و Lucide را در همان build بررسی می‌کرد؛ این اثبات یکتایی همهٔ helperها یا نبود نسخه‌های متفاوت کتابخانه نیست. Temporal همچنان در chunk تقویم است.
- service worker وب همهٔ فایل‌های static build را precache می‌کند؛ تقسیم chunk برای کاهش Initial است و به معنی کاهش دانلود پس‌زمینهٔ وب نیست. زمان اجرا و حافظهٔ Android واقعی اندازه‌گیری نشده‌اند.
